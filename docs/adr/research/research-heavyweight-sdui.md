# Research: heavyweight server-driven UI for LiveView apps

Research notes, 2026-11-10. This extends [the progressive mobile enhancement proposal](../0007-progressive-mobile-enhancement.md) with a coordinator design and a source audit. The audit is static. Device builds, performance, and compatibility with FoW's current Phoenix version are open questions.

## Navigation contexts and what the browser already gives us

Hotwire Native supports a single native navigation stack around web content. Tabs are optional. In its tab setup, each tab gets a navigator and its own stack. On iOS, a session reuses one WKWebView across its pushed view controllers. The lazy-tab option defers the first visit to a tab root until selection. That reduces startup work, but the documented option offers no eviction policy for tabs already visited or guarantee that their routes work offline. A native screen can also sit on the stack. [How it works](https://native.hotwired.dev/overview/how-it-works) · [iOS tabs](https://native.hotwired.dev/ios/tabs) · [Android tabs](https://native.hotwired.dev/android/tabs) · [Session and shared WebView](https://github.com/hotwired/turbo-ios/blob/main/Docs/Overview.md)

A **navigation context** is a tab's route stack, scroll position, and restoration state. It can have a dedicated WebView or use a shared one. A web shell can also keep one document and explicitly manage per-tab stacks. Iframes provide separate browsing contexts, but each LiveView in a frame still needs its own connection and coordination for Back, focus, and FoW recovery. Multiple WebViews buy isolation and retained tab state, at the cost of more live views, more bridge instances, and a policy for suspending or evicting tabs. Compare both with one WebView before standardizing on either. Measure cold start, memory after visiting five tabs, server processes with background tabs, and restoration after the OS reclaims a WebView.

A running LiveView already gives the wrapped web app route changes, history, efficient server diffs, DOM reconciliation, local hook code, CSS layout, and browser controls. A responsive bar and web transitions are a useful baseline. Native chrome earns its place through things such as platform Back gestures, safe-area behavior, accessibility, and integration with OS presentations. Those are comparisons to make on devices. The Economist app is a design reference for the experience, with its implementation unverified. [LiveView JavaScript interop](https://phoenix-live-view.hexdocs.pm/js-interop.html) · [Hotwire Native navigation](https://native.hotwired.dev/reference/navigation)

## Coordinator proposal: let hooks share their local behavior

Today the FoW coordinator destroys the outgoing LiveView owners on cached navigation. The presenter reconstructs an allowlisted DOM region and strips hook bindings. The JS bundle stays alive. This is a good seam for local lifecycle callbacks. LiveView's server `mount/3`, its JS `mounted` callback after a live join, and a cached DOM insertion are separate events. On a cold offline launch a component may need to appear before the socket joins, so wait for both its element and the bridge capability handshake, using document boot or the cached presentation commit. [FoW coordinator](../../../priv/static/js/fog-of-war-coordinator.js) · [Snapshot presenter](../../../priv/static/js/fog-of-war-presenter.js) · [LiveView hook interface](https://phoenix-live-view.hexdocs.pm/js/interfaces/HookInterface.html)

Propose an opt-in registry of local controllers with `mount(element, props, context)`, `update(props, context)`, and `dispose()`. An ordinary `phx-hook` delegates its local work to the same controller. Its live adapter can separately provide `pushEvent` and server event subscriptions. The cached adapter supplies the element, validated props, a local bridge, and local navigation. It has no LiveView transport. A mounted widget can still handle local taps, native replies, and a local draft or preference. Committing application data offline would need its own persistence and synchronization rules.

| Trigger | Owner and behavior |
| --- | --- |
| Connected page mounts or patches | The real hook owns the controller. Its `mounted` and `updated` calls apply props. `destroyed` disposes it. A socket disconnect while the DOM stays in place can update capability state without remounting the widget. |
| Bundled cold start or cached navigation | The coordinator mounts only registered descriptors after the active region commits. The allowlist carries a component name, stable key, and validated data. The JS registry supplies the implementation. Enable local controls only within the opted-in component. The existing offline event capture currently blocks buttons, inputs, and related events. |
| Back, cached replacement, or live handoff | Dispose the outgoing controller and its native presentation before mounting the incoming one. Scope bridge requests to a document generation and presentation key so late replies cannot revive removed UI. The host also clears document-owned resources on reload, WebView destruction, or process loss, where JS teardown may never run. |

For the first bridge contract, use a small message envelope with a version, WebView/context ID, document generation, component key, and revision. Support capability negotiation, presentation, prop replacement, dismissal, and a small set of allowed native events. Keep HTML visible until native presentation succeeds. Native taps request the same routes as web taps and highlight the tab that actually commits. A shell tab bar lives above route transitions. An exhibit sheet or full-screen overlay belongs to a route and dismisses when that route leaves. System Back dismisses the overlay first and then returns to the route history. Preserve a visible fallback if a native screen is unavailable.

Hotwire Native's named, capability-checked Bridge Components and Stimulus's DOM lifecycle are useful precedents. We can implement an explicit FoW commit seam first and later compare it with a DOM observer or custom elements. Those would observe attachment automatically but would still need ownership rules to avoid two controllers mounting the same view. [Bridge Components reference](https://native.hotwired.dev/reference/bridge-components) · [Stimulus lifecycle](https://stimulus.hotwired.dev/reference/lifecycle-callbacks)

## LiveView Native source audit

The original Elixir library negotiated formats and dispatched to format-specific render modules, such as SwiftUI and Jetpack. That model can share server state and event handlers, with separate platform templates. Our proposed experiment would send HTML and an optional native descriptor together through one ordinary web LiveView. A capability check decides whether the wrapper presents the native surface. This preserves the browser's LiveView connection and patch pipeline and gives a cached page enough data to open the same surface offline. [Elixir format dispatch at 41ebb3d](https://github.com/liveview-native/live_view_native/blob/41ebb3d0104a14ad3b70acb561c62d5499d1bb01/lib/live_view_native/live_view.ex)

**Core.** The Rust `Document` parses markup and also accepts LiveView fragment JSON. The merge path applies a fragment to the retained template, renders the result to a string, parses the new document, diffs it against the existing document, and applies node patches. The FFI layer emits add, remove, change, and replace notifications with node references and parent information where applicable. There are separate costs for the network diff, the local document merge, and the platform render. A small wire diff can still cause a whole-document parse. The standalone markup parser is a possible reuse point if the browser supplies the complete native subtree. Measure it separately from the LiveView fragment machinery. [Core document at 2f0e874](https://github.com/liveview-native/liveview-native-core/blob/2f0e874960ee93b5b76daff2ecfb6d8e445e15bc/crates/core/src/dom/mod.rs) · [Core FFI](https://github.com/liveview-native/liveview-native-core/blob/2f0e874960ee93b5b76daff2ecfb6d8e445e15bc/crates/core/src/dom/ffi.rs)

**SwiftUI.** The coordinator merges fragment JSON and listens to Core's document changes. A changed element can notify its own observers, while text and structural changes may invalidate the parent. This is the most relevant precedent for preserving native identity under updates. The custom element registry and stylesheet modifier decoders are distinct reuse candidates. The stylesheet accepts a Swift-like modifier language and decodes supported modifiers. It is worth trying a small markup string and one style rule in a local host, then measuring how much of the session coordinator, generated registry, and Swift package graph comes along. [SwiftUI coordinator at 79479ca](https://github.com/liveview-native/liveview-client-swiftui/blob/79479ca56ac029937c2ad66fb3a98393fe57ecb3/Sources/LiveViewNative/Coordinators/LiveViewCoordinator.swift) · [Custom elements](https://github.com/liveview-native/liveview-client-swiftui/blob/79479ca56ac029937c2ad66fb3a98393fe57ecb3/Sources/LiveViewNative/LiveViewNative.docc/AddCustomElement.md) · [Stylesheet modifiers](https://github.com/liveview-native/liveview-client-swiftui/blob/79479ca56ac029937c2ad66fb3a98393fe57ecb3/Sources/LiveViewNative/LiveViewNative.docc/AddCustomModifier.md)

**Jetpack Compose.** The Android coordinator handles initial rendered payloads, subsequent diffs, navigation, and events. Its `DocumentParser` merges fragment JSON into Core and then walks the entire document into a `ComposableTreeNode` tree. The coordinator publishes the new root. The change callbacks in that parser log node changes. They do not drive targeted Compose updates there. The tag-to-factory registry, modifier adapters, and component tests are useful candidates. Audit Compose keys and remembered state before assuming the Swift invalidation strategy is portable. [Android coordinator at c0b88e4](https://github.com/liveview-native/liveview-client-jetpack/blob/c0b88e498db62770ee5b8bd47a8f30145b05fe19/client/src/main/java/org/phoenixframework/liveview/foundation/domain/LiveViewCoordinator.kt) · [Document parser](https://github.com/liveview-native/liveview-client-jetpack/blob/c0b88e498db62770ee5b8bd47a8f30145b05fe19/client/src/main/java/org/phoenixframework/liveview/foundation/data/mappers/DocumentParser.kt) · [Compose registry](https://github.com/liveview-native/liveview-client-jetpack/blob/c0b88e498db62770ee5b8bd47a8f30145b05fe19/client/src/main/java/org/phoenixframework/liveview/foundation/ui/registry/ComposableRegistry.kt)

**Project history and maintenance.** DockYard documented the Rust extraction as a multi-month effort to share client functionality across platforms. That is evidence of integration cost. It does not establish why work slowed or stopped. GitHub metadata on this pass marked the Elixir repository archived and the three client/Core repositories unarchived. The inspected clients also pin different Core release candidates: SwiftUI to 0.4.1-rc-5 and Android to 0.4.1-rc-2. The four inspected source trees have MIT license files. A reuse pass should check the chosen revision and transitive dependencies, then build against current Xcode and Android tooling. A proper postmortem still needs maintainer accounts and shipped-app evidence. [DockYard's Core integration update](https://dockyard.com/blog/2023/01/17/liveview-native-yearly-update) · [Swift package](https://github.com/liveview-native/liveview-client-swiftui/blob/79479ca56ac029937c2ad66fb3a98393fe57ecb3/Package.swift) · [Android dependency catalog](https://github.com/liveview-native/liveview-client-jetpack/blob/c0b88e498db62770ee5b8bd47a8f30145b05fe19/gradle/libs.versions.toml)

## From a native overlay to a native scene tree

A full-screen takeover can start with a compiled Mob screen presented over the WebView. The bridge selects a known screen and passes props. A subsequent step could render a bounded tree of native primitives from an inert descriptor shipped with the HTML. The browser remains the protocol client and publishes new descriptor revisions when LiveView patches that subtree. Offline, a cached descriptor can instantiate the same tree, and local events can drive further changes.

Start by replacing the **descriptor** for one small screen and letting the native renderer preserve view identity by key. Avoid rebuilding the WebView or clearing a native text field, scroll position, focus, or selection when a sibling changes. If profiling shows descriptor replacement is costly, introduce keyed operations such as insert, remove, move, and set props, committed as a batch. An interrupted or out-of-order batch needs a full-tree recovery path. Keep stable keys across LiveView DOM replacement. DOM IDs alone may only be unique within a particular route or WebView. The host must scope keys to that owner and apply visual changes on the native UI thread.

Mob already renders declarative trees in an Elixir host, with built-in widgets and platform factory registrations for extensions. Probe what state survives an updated keyed tree before adding a second reconciler. It can give the app one shared shell and a shared component vocabulary. Platform glass, custom native views, and build configuration still require platform work. A small supported design-system vocabulary keeps unsupported payloads recoverable through the HTML fallback. [Mob components](https://mob.hexdocs.pm/components.html) · [Mob native factory registration](https://mob.hexdocs.pm/Mob.Component.html)

Airbnb's Ghost Platform provides a useful design-system target: clients share a vocabulary for screens, sections, and actions while platform frameworks supply their own implementations. Consider a versioned set of components and tokens before exposing platform-specific modifier languages. React Native's Fabric is a separate comparison: it derives a shadow tree from client-side React, computes layout, and commits batches of native mutations. Its lessons about stable identity, native state, atomic updates, and measurement apply even with a server-authored tree. Adopting React Native itself would add a JS runtime, bundle, and native renderer integration to the shell. Compare that cost against Mob and extracted LiveView Native pieces for the same screen. [Airbnb Ghost Platform](https://medium.com/airbnb-engineering/a-deep-dive-into-airbnbs-server-driven-ui-system-842244c5f5) · [React Native render, commit, and mount](https://reactnative.dev/architecture/render-pipeline)

## Probes to decide what to ship

1. **Web baseline.** Build the museum's Explore, Saved, and Visit flow as mobile web. Exercise cold cached startup, Back, a missing route, reconnect, and tablet layout. Identify which parts benefit measurably from native treatment.
2. **Bridge and lifecycle.** Add a floating shell bar and one exhibit sheet. Exercise a live patch, cached navigation, offline local action, Back, reload, and a reply arriving after the user leaves. Check that one control is mounted at a time, that native fallback works, and that web and native agree on the selected route.
3. **Renderer scavenger pass.** On both platforms, attempt to instantiate a three-control tree without a Phoenix connection. Patch one label, reorder a keyed row, and remove a focused input. Trace what code must be extracted, what state survives, and what fails with current toolchains. Compare Mob and the LiveView Native renderers before selecting a reuse boundary.
4. **Heavyweight comparison.** Use the same screen and interaction trace to compare full descriptors, keyed patches, and a Fabric-backed prototype if the first two fall short. Record bridge payload size, commit latency, peak memory, accessibility, and developer steps for adding a component and a style. Test a cached descriptor against an older binary to establish version and fallback behavior.

The decision this research should enable is how far to go per app: a wrapped website, native chrome and a few bridged controls, or a native renderer for selected screens. A successful small bridge demo establishes the lifecycle seam and leaves the renderer choice open.
