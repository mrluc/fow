# ADR-002 research: serving bundled assets over loopback

## Findings

- `http://localhost` and loopback IP URLs (`127.0.0.1`, `::1`) are commonly treated as **potentially trustworthy** by the Secure Contexts model. This is a secure-context classification; it does not mean HTTP is encrypted, and it does not promise every embedded WebView uses the same policy. The W3C Mixed Content rules allow requests whose URL is potentially trustworthy, while ordinary insecure HTTP URLs remain mixed content. In a secure document, scripts and fetch/XHR are blockable mixed content; ordinary images and CSS backgrounds are generally upgradeable, but CORS-enabled images are blocked. Thus “localhost is trustworthy” is not a blanket permission for arbitrary HTTP content. [Secure Contexts](https://www.w3.org/TR/secure-contexts/) · [Mixed Content](https://www.w3.org/TR/mixed-content/)
- **Platform rules still matter.** Android WebView defaults to `MIXED_CONTENT_NEVER_ALLOW` for apps targeting Lollipop or later; its compatibility mode is intentionally not fully specified and `ALWAYS_ALLOW` is discouraged. Apple ATS is a separate networking policy: current Apple documentation describes local-network ATS exceptions and version-specific behavior for IP addresses; `NSAllowsArbitraryLoadsInWebContent` relaxes ATS for WebView connections but does not change WebKit’s secure-context/mixed-content decisions. Apple’s local-network permission disclosure applies to apps that use the local network, but the reviewed docs do not settle whether a server bound strictly to the device’s own loopback triggers the user-facing permission prompt on each supported OS. [Android `WebSettings`](https://developer.android.com/reference/android/webkit/WebSettings#setMixedContentMode(int)) · [Apple `NSAllowsLocalNetworking`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking) · [Apple `NSLocalNetworkUsageDescription`](https://developer.apple.com/documentation/bundleresources/information-property-list/nslocalnetworkusagedescription)
- **Phoenix CORS is only one layer.** Correct `Access-Control-Allow-Origin` and credential headers can authorize cross-origin script `fetch`/XHR responses after the browser permits the request. CORS cannot make an insecure URL potentially trustworthy, override mixed-content blocking, change ATS or Android WebView policy, or grant local-network access. It also does not authorize WebSocket upgrades: Phoenix’s WebSocket `check_origin` is a separate origin check and should remain enabled with the intended origin allowlisted. [Phoenix security guide](https://phoenix.hexdocs.pm/security.html) · [Phoenix Endpoint `check_origin`](https://phoenix.hexdocs.pm/1.8.16/Phoenix.Endpoint.html)

## Origin choice for LiveView

Serving the **whole document from loopback** changes the page origin to `http://localhost:<port>` (or the loopback IP and port). Relative `/live` therefore targets the local server, not the production Phoenix endpoint. Pointing the socket explicitly at production instead makes it cross-origin: it presents the loopback page’s `Origin`, needs server-side origin policy changes, and the browser will not attach cookies scoped to the production host to requests for localhost. A localhost-hosted page also cannot inherit the production site’s cookie/session merely by enabling CORS. Phoenix LiveView relies on its normal page/session bootstrap; serving a copy of the HTML locally does not itself establish the production HTTP cookie session.

Keeping the **real HTTPS document origin** preserves same-origin `/live`, normal production cookies, Phoenix origin checks, and LiveView’s ordinary bootstrap. It is the lower-friction fit for LiveView. The unresolved part is how to deliver local assets into that origin: a loopback HTTP asset URL is governed by the WebView’s mixed-content/request policy, and a custom scheme is governed by WebKit’s scheme semantics. The native probe already recorded in this project is direct evidence for the latter: `fog-of-war-assets://` displayed plain `<img>` and CSS background assets, but blocked CORS images/fetch and external scripts/styles. Do not infer from desktop browser localhost behavior that WKWebView/iOS/macOS or Android WebView will allow the required resource types; test the actual OS and WebView versions with the exact URL form and asset request modes.

## Confidence and next verification

High confidence: potentially-trustworthy and mixed-content are distinct checks; active script/fetch restrictions are materially different from plain image display; Phoenix CORS cannot repair a load rejected before CORS or configure a WebSocket origin check. Medium confidence: loopback server responses should be eligible as potentially trustworthy in the target WebViews, since vendor docs found here do not explicitly guarantee the web-platform exception for every embedded WebKit version. Unsettled: whether the proposed listener at `localhost` versus `127.0.0.1`, local-network privacy prompts, ATS settings, and exact CSP/CORS headers produce consistent behavior across supported iOS/macOS/Android versions. Record device/OS/WebView version, page origin, resource URL, request mode, console/network failure, and whether ATS or local-network permission is involved in the next native probe.
